# Witching Gadgets: Reforged

Port of Witching Gadgets 1.1.10 (MC 1.7.10, BluSunrize) as an addon to Thaumcraft 4: Reforged (`../thaumcraft-4-reforged`, "the base" below) for Minecraft 26.3 on NeoForge. Logic, numbers, recipes, texts and assets of the original are carried over 1:1, the technical side is written on modern APIs.

This file describes how to develop and port the mod. Phase status, test counts, run dates and log paths do not belong here. Add a line only if an agent would make a mistake without it: a non-obvious API rule, a required order of steps, or a deliberate deviation from WG that would otherwise get "fixed" back.

## Principles

- Source of truth for behavior: the WG 1.1.10 sources in `reference/wg-src` (branch `master`, `tools/fetch_wg.py`). WG code is read as data, nothing from it is executed.
- Integrations with other mods (TConstruct, Twilight Forest, Mystcraft, Magic Bees, ForgeMultipart, MineTweaker) are excluded, except JEI.
- Travellers' Gear 1.7.10 (BluSunrize) is ported into the addon by decision of the user, sources in `reference/tg-src` (`tools/fetch_tg.py`, read as data like WG). Its four slots (cloak, pauldron, vambrace, title, `gear/GearSlot` in TG order) live behind `platform/Gear`; items implement `gear/GearItem`. Belts and rings use the base bauble slots (`thaumcraft.platform.Baubles`) like TG. Mariculture, Tinkers', Botania and the old packet pipeline are integrations and are not ported.
- The WG coremod (`witchinggadgets/asm`) is not ported as ASM, the required behavior is done with NeoForge events or mixins.
- WG bugs are fixed only if they break the game (dupes, item loss, NPE, desync, server crash). Gameplay quirks stay.
- The server validates what WG trusted from the client. Client classes never leak to the server, everything must work on a dedicated server.
- Resources are made by Python generators in `tools/`, datagen is not used. `gen_resources.block_model` gives every element model without a parent `minecraft:block/block`, otherwise the block item has no GUI transforms and renders flat.
- The original has no license specified, the port is `All Rights Reserved` for personal use.

## Environment

- Mod `witchinggadgets`, package `witchinggadgets`, asset namespace `witchinggadgets`, archive `witching-gadgets-reforged`, version 1.0.
- MC 26.3, NeoForge 26.3.0.57-beta, ModDevGradle 2.0.148, JEI 31.9.0.58, REI 26.3.824 (dev runs use JEI, REI with `-Precipe_viewer=rei` like the base), TerraBlender 26.3-26.3.0.0.9, Java 25. Versions in `gradle.properties` match the base.
- Python 3, `tools/` scripts have no external dependencies.
- The base is included as a composite build: `includeBuild("../thaumcraft-4-reforged")` in `settings.gradle`, dependency `implementation "thaumcraft:thaumcraft-4-reforged:1.0"`. The base repository must sit next to this one. The base is not edited from the addon.
- `neoforge.mods.toml`: the `thaumcraft` dependency is required with `ordering="AFTER"`, so the addon constructor runs after the base constructor. Research and recipes are registered from the addon constructor.
- `runGameTestServer` runs with `--tests witchinggadgets:*`, base tests are not run. The test structure `witchinggadgets:test/platform` (7x7x7 stone floor) is generated by `tools/gen_testing.py`; the base no longer ships one.
- `run/` needs `eula.txt` with `eula=true` (gitignored).
- There is no root `icon.png` or `poster.png` yet, `logoFile`/`iconFile`/`bannerFile` in `neoforge.mods.toml` are added together with them.

## Architecture

- `platform/` and `client/platform/` hold everything where version APIs diverge. The addon has its own seams in the `witchinggadgets` namespace: `WgNetwork` (its own `RegisterPayloadHandlersEvent`), `client/platform/WgClientNetwork`. Gameplay code goes only through them and through the base seams. `tools/check_seams.py` fails on forbidden imports outside the seams and on client class imports outside `client/`.
- Mouse buttons on 26.3 are SDL3 numbers: left is `InputConstants.MOUSE_BUTTON_LEFT` (1), right `MOUSE_BUTTON_RIGHT` (3); never compare with 0/1.
- Registration: `registry/` (`ModItems`, `ModBlocks` with `withItem`, `ModBlockEntities`, `ModMenus`, `ModEntities`, `ModEffects`, `ModSounds`, `ModCreativeTabs`), payloads in `network/ModPayloads`, client handlers in `client/ClientPayloadHandlers`, client entry point `client/WitchingGadgetsClient`.
- `Config` is SYNCED only, keys and defaults are carried over from `WGConfig`.
- The creative tab is the addon's own; its icon is the hidden `tab_icon` item, the WG wall mirror (`ItemRenderWallMirror`) rebuilt by `gen_tab.py` as an item model: the WG `TileRenderWallMirror.shape` gold pixels as 1x1x1 elements mapped onto a generated palette texture, and the WG glass strip as a flat plane.

## Feature layout

- A feature lives in `witchinggadgets/<feature>/` and exposes one `<Feature>Feature` class: static `DeferredHolder`s in the shared registries, methods `load()` (empty, needed to load the class), `research()`, `recipes()`, and `aspects(AspectRegistry)` when needed.
- A feature adds one line each to the shared files: `Features.java`, `client/ClientFeatures.java`, `tools/features.txt`, `network/ModPayloads.java`, `client/ClientPayloadHandlers.java`. These files use `merge=union` in `.gitattributes`, write lines as separate statements.
- A feature's GameTests live in `test/<Feature>GameTests.java` on `WgGameTestSuite` (`new WgGameTestSuite("name").add("test", body)`, registered with one line in `Features.tests`).

## Research

- `research/WgResearch`: category `WITCHGADG` (registered in `WgResearch.init()` from the constructor), factories `item(...)` and `fake(original, originalCategory, column, row, icon)`, pages `text(page)`, `recipe`, `arcane`, `infusion`, `enchant`, `crucible`, `compound`. The WG code ports almost line by line: `new ResearchPage("witchinggadgets_research_page.KEY.1")` is `WgResearch.text("1")`, `(ShapedArcaneRecipe) recipeList.get("KEY")` is `WgResearch.arcane("KEY")`.
- `WgResearchItem.setPages` turns a text page without a dot into `tc.research_page.<key>.<page>` (`1`, `2`, `r1` like WG, no renumbering), a full key stays. `.when(BooleanSupplier)` hides research by config (mirror research uses `thaumcraft.Config::allowMirrors` like WG `Config.allowMirrors`), `.setWarp(n)` is WG `addWarp(n)`. WG `setParents` validated parents and dropped the research on a typo; the port does not, the table test catches it.
- `WgFakeResearchItem` is WG `WGFakeResearchItem`: key `WGFAKE<original>`, stub, hidden, complexity 1, no aspects, name, text and pages delegated to the base research, appended to the original's siblings in the constructor. All 12 links live in `research/BaseResearchLinks` and are registered before `Features.research()`, feature research uses them as parents.
- `tools/extract_wg_research.py` builds `tools/wg_research.json` from `WGResearch.registerResearch()` with a small statement interpreter over `tools/wgjava.py` (the Thaumic Tinkerer expression parser). `CONDITIONS` fixes WG branches: Twilight Forest absent (no `CLOAK_RAVEN`), mirrors on, native clusters and transmutations of other mods' ores off (`METALLURGICPERFECTION_CLUSTERS`, `METALLURGICPERFECTION_TRANSMUTATION`, `WGFAKETRANSIRON` are not ported), no `tempus` aspect. `CLOAKKAMA_4` (raven) is dropped from the kama page. Aspects are stored as base tags (`praecantatio`), read from the base `Aspect.java`.
- GameTest `research_matches_wg_table` compares every registered table entry (position, complexity clamped to 1..3, flags, parents, siblings, triggers, aspects, warp, pages, fake target) and fails on WG research missing from the table. Every WG research entry is ported, so a missing entry fails the test. Do not edit the table by hand, rerun the extractor and compare with WG.

## Recipes

- `crafting/WgRecipes` on top of `TcRecipes.register`: `arcane(key, research, result, aspects, pattern, 'A', ingredient, ...)`, `arcaneShapeless`, `infusion(key[, research], result, instability, aspects, central, components...)`, `enchantment(key, research, enchantment, instability, aspects, components...)`, `compound(key, research, aspects, width, height, depth, blocks...)`, `crucible`, `vanilla(key, research, recipePath, result)`. A repeated key (including base keys) throws `IllegalStateException`.
- Recipe keys are WG `tag + tagAddon` (`BAGOFTRICKS_CLOTH`, `CLOAKKAMA_0`), the research of a recipe is WG `tag`.
- Base ids of TC4 references come from `tools/tc4_refs.json` (copied from Thaumic Tinkerer, built by `tools/tc4_ref.py --all` from the base `reference/decompiled`): `ConfigItems.itemResource` meta 7 is `thaumcraft:enchanted_fabric`, `ConfigBlocks.blockCosmeticSolid` meta 6 `thaumcraft:arcane_stone`.

## Content notes

- Gear slots on 26.3 mirror the base bauble implementation in `platform/gear` (attachment `gear` with sync and copy on death, drops on death without keepInventory, `OpenGearPayload`) and `client/platform/gear` (key `G`, a button at (66, 20) of the inventory and the base baubles screen, the WG `wg.desc.gearSlot.tg.N` text as the empty slot tooltip); the screen is the TG inventory (see Travellers' Gear). On 1.21.1 the same API sits on Curios slot types.

- `materials/MaterialsFeature` registers all 14 `WG_Material` metas and the void metal block. Their behaviour (abacus, iconographic plate and photo, guiding string, gemcutting tools) arrives with the features that use them. The three cloths share `mat_cloth` tinted with the aspect colour like WG `getColorFromItemStack` (Vacuos `0x888888`, Lucrum `0xE6BE44`, Praecantatio `0x9700C0`). Item aspects follow WG `postInitThaumcraft`.
- Spinning wheel: the WG TESR is static (the `animation` counter is never used), so `tools/gen_spinning.py` turns the 17 `ModelRenderer` boxes into a block model without a BER. The model is in the WG facing 5 (east) orientation, the blockstate rotates it with `y` 0/90/180/270 for east/south/west/north; WG renders without the usual entity flip, so side faces are upside down and the UVs keep that. The facing is opposite to the player's look like WG `onBlockPlacedBy`. WG unflipped `ModelRenderer` boxes go through `tools/boxmodel.py`.
- `spinning/SpinningRecipe` is WG `SpinningRecipe`: unordered, the number of filled input slots must equal the number of inputs, one item is taken from every input slot. Progress counts to 120 and the craft happens on the next tick (121 ticks per item), like WG. All six slots accept items from hoppers like WG `IInventory`; only the GUI output slot refuses placement. The GUI progress bar is synced through `ContainerData`.
- Cloaks (`cloaks/`): the storage and wolf cloaks are made from the TG cloak (`traveller_cloak`, WG `travelgearCloakBase`), the kamas from the TG belt or the base mundane belt (`baubleBeltBase`). Cloaks sit in the gear CLOAK slot, kamas in the base belt bauble slot; `CloakEvents.activeCloak` prefers the cloak slot. Activation through the TG ability menu opens the 27-slot storage (`STORAGE` component, `gui/bagcloak.png`) or toggles spectral. Spectral and its upkeep draw 1 Aer from a wand in the inventory (the base vis amulet has no consumption API); targets of non-boss, non-eldritch mobs without goggles/revealer are dropped, all interaction is cancelled, and other clients without goggles skip rendering the player. In-place stack changes call `Gear.sync`. Item stack keys live in `CloaksFeature` so they register before items. `client/geom/CloakGeometry` is the WG `ModelCloak`/`ModelKama` tessellation in the original model space (translate 0, 1.45, 0, scale 1, -1, 1) drawn in `CloakLayer` after `body.translateAndRotate` (crouch); the client config `cloakAnimationMode` (default 2, stretch) matches WG. The raven cloak needs Twilight Forest and is skipped. The kama recipe does not carry over colour or stored items (WG lost them on shift-click too).
- Bags (`bags/`): `BagKind` TRICKS, VOID, ENDER, HUNGRY like WG `ItemBag` metas 0-3. 18 slots on `gui/bag.png`, contents in `bag_contents` (filters for the void bag), owner by player name like WG (`bag_owner`, `bag_unlocked`; strangers take 4 magic damage and drop the bag, the owner toggles the lock with sneak + use) for TRICKS and HUNGRY. The void bag has 18 ghost filter slots (`VoidBagMenu`, `gui/voidbag.png`); a filtered ground pickup is destroyed and one random primal of its aspects goes to a hotbar wand with room. The hungry bag swallows ground pickups into its storage (stacks up to 64). The ender bag opens the ender chest. Pickups go through `ItemEntityPickupEvent.Pre`, which fires before the pickup delay check, so `BagEvents` skips items with a delay. The held bag's hotbar slot is locked and bags do not fit into bags. Dyeable like WG with per-kind default colours. The runic cloak (`ItemRunicCloak`) is not registered in WG 1.1.10 and is not ported.
- Wearables (`baubles/`): WG `ItemMagicalBaubles` split into items; shoulders, vambraces and the title go to the gear slots, rings to base ring slots. The TG bases `pauldron`/`vambrace` are the TG simple gear (TG recipes and textures). Attribute bonuses are transient modifiers re-added every tick. The luck ring replaces the WG coremod with `GetEnchantmentLevelEvent` on the main-hand stack of a wearer. The silver ingot in the infusions is iron (WG used iron without a silver mod). The lucky coin is `thaumcraft:gold_coin` with fortune and looting (`witchinggadgets:lucky_coin` data key, enchanted through the server registries). Title drops lost the looting bonus. `client/baubles/BaubleLayer` draws the WG `ModelMagicalBaubles` arm boxes for shoulders and vambraces in the gear slots.
- Bewitched robes (`robes/`): material from WG `armorMatSpecialRobe`, equipment asset `bewitched_robe` with the WG `advancedRobes_1/_2` layers copied by `gen_robes.py`; the chest uses the WG `ModelRobeSkirted` (`client/robes/SkirtedRobeModel`, 128x64, hood hidden under a non-goggles helmet), the leggings the plain armor model like WG. Wolves drop wolf pelts like the WG `EventHandler` (`materials/MaterialEvents`).
- Arcane stone devices (`arcanestone/`): the ethereal wall network is the face-connected set of walls (`EtherealWallBlock.network`, capped at 1024) and every wall carries `powered` in its blockstate, updated by a flood fill on neighbour changes instead of the WG master objects; powered walls have no collision. The disguise is a full block with a plain model, stored in the block entity and rendered through the base `thaumcraft:warded` blockstate model via `platform/CamoBlockEntity` (on 1.21.1 the base `CamouflagedBlockEntity`); sneak + empty hand removes it, the disguise light is used. The ageing stone ticks every baby/parent in the WG 7x5x7 box by one. The stone extruder is a static block model built from the WG TESR boxes (`gen_arcanestone.py`, the water column tinted by a block tint source, the Thaumcraft bore texture replaced by arcane stone since block models only see the block atlas, no cobble preview), `powered` in the blockstate hides the fluids, a wand turns it to the clicked face (sneak: opposite).
- Wooden devices (`devices/`): the sauna stove keeps WG's flood fill (30 cells per tick, 1200 cells, radius 8, 6 up or 2 over water, 5 down) but merges the cells into boxes in one greedy pass instead of WG's box loop, whose `outlineMaxZ` typo could stall it. A bucket lasts 1200 counts decremented every 10 ticks. The stove ticks on both sides like WG and syncs its tank and counter; the steamed players live in separate server and client maps. WG sweat particles are vanilla falling water. Client effects of common blocks go through `fx/WgFx`, set by `client/devices/DevicesClient`. The aspect library has a virtual output slot: taking it consumes one input label, hoppers can only insert labels, and the aspect is chosen with `clickMenuButton` checked against the server's knowledge. Its model is the WG upside-down arcane workbench with books on top (the WG TESR without the entity flip); the labels are drawn by `client/devices/LabelLibraryRenderer`.

- Gadgets (`gadgets/`): the arcane abacus, guiding string and photo items stay registered in `MaterialsFeature` but use classes from `gadgets/`; research, recipes, stack keys and the scan camera live in `GadgetsFeature`. The abacus reads any base `Node` block entity (aura nodes and node jars) and repeats the WG matrix scan (pedestals from 10 below to 5 above, pedestals above or beyond 8 blocks only warn), it does not reuse the base matrix symmetry, so the WG warnings stay.
- Guiding string: the server records turns in `GadgetEvents` (player tick over the whole inventory, like WG `onUpdate`), the client draws the path with `client/gadgets/GuideBeamFx` (base `PowerBeamGeometry`, refreshed every tick like TC4 `beamPower`) only for the main-hand string.
- Scan camera and photos: the plate stores a `ScanSnapshot` (kind, key, aspects, clue, name) taken at shot time instead of the WG serialized entity, so a photo of a node keeps the aspects of the moment. WG lost the photo when the inventory was full and consumed a developed photo even when the scan was invalid; both are fixed. Developed photos stack to 64 because the WG developing recipe makes one copy per paper and a stack above its limit cannot be saved. Developing is a base dynamic arcane recipe (no research check, like WG); `SCANCAMERA_DEVELOP` is a display recipe whose plate needs the `witchinggadgets:scan` data, so it never wins over the dynamic one. Ink sacs count as black dye (WG `dyeBlack`). The camera model is the WG `.obj` through `neoforge:obj` (`gen_gadgets.py` assigns one material per object, drops `Display_00`, centres it on the block); WG's first-person arms holding the camera are not drawn. TC4 has no `cameradone` sound, only `cameraticks` plays.

- Gems (`gems/`): gem cut and aspect live in the `gem_cut`/`gem_aspect` components, Brilliance and Brittle are data-driven enchantments (`gemstone_potency`/`gemstone_brittle`, only on the infused gem, never offered by tables) set through the server registries. Base gems are matched by `c:gems/*` tags instead of WG ore names (no `gemPrimordial`). Gems take durability 32 like WG `getMaxDamage`, so they never stack. The cutting table output is virtual (slot 4 is computed, never stored): WG dropped it on break and let hoppers pull it for free, both fixed; shift-click crafts one gem per loop like vanilla results. Gemcutter's tools turn a base `thaumcraft:table` into the table without being used up (WG `onItemUse`); the compound recipe only feeds the research page. The table model is the WG `ModelCuttingTable` boxes as a block model, flasks and essence bowls with the aspect colour and the gem on top are drawn by `client/gems/CuttingTableRenderer`. Oval Ordo has no global node index in the base, so it looks for the closest loaded node within 8 chunks; oval Perditio accepts the clicked mirror as well as the block in front (WG only checked the block in front, which made it useless); oval Terra uses the base ore scan FX for 50 s; oval recharge from a vis relay runs on the server only (no client beam). The glimmer of light is the addon's own invisible light block with a lifetime.
- Crystal capsule: the fluid id lives in `capsule_fluid`; it works like WG on any source liquid block and on fluid handlers (`Transfer`), and from dispensers. The item model tints a mask layer with the fluid colour (`client/platform/WgItemTintSources`: the fluid model tint, lava orange, otherwise the block map colour) instead of drawing the fluid texture.

- Infusion enchantments (`enchantments/`): data-driven, treasure-only (no table tags), JSON and `supported_items` tags from `gen_enchantments.py`; the base infusion still demands a damageable single item, so gear-slot items never get them. Translucency hides armor by clearing the equipment of the avatar render state (`client/enchantments/EnchantmentsClient`, WG `SetArmorModel` result -2, so level 1 hides instead of the translucency the text promises). Unveiling draws sparkles around invisible players on the client tick instead of every frame and does not change spectral cloak rendering (goggles already show spectral players). Stealth keeps the WG fallback: a failed roll still drops the target when a non-boss creature within 5 blocks already targets the player. Throwoff only checks the helmet like WG; the vanilla server never lets an entity ride a player (`Player` cannot serialize), so it triggers only for modded riders.

- Primordial armor (`primordial/`): the pieces extend the base `FortressArmorItem`, so the base fortress reduction (magic, fire, explosions, set bonus over head/chest/legs) already applies; `PrimordialEvents` adds only the WG extras on top: Ignis 0.75 per piece times the WG set factor (all four slots) against fire and explosions plus extinguishing, Terra defense/50 per piece against armor-bypassing damage. Aer turns projectiles within 4 blocks back to their owner and cancels projectile damage, Aqua cures blindness, poison, wither, nausea and taint poison, Ordo replaces the WG coremod with `MobEffectEvent.Applicable` (warp effects reapplied with amplifier minus Ordo pieces and duration divided by pieces + 1), Perditio blinds and slows attackers one hit in four. Every piece and weapon cycles its own affinity through the TG ability menu like WG (no sneak + use). TC4 infusion fired the crafting event WG used to return 3 powerless pearls; the base does not, so the armor recipes mark the result with `primordial_pearls` and the player tick gives the pearls once (to the player, not at the matrix). The model is the WG `ModelPrimordialArmor` as two layer definitions (0.0625 and 0.3125 for the boots), visibility per slot in `setupAnim`.
- Primordial weapons share `primordial/PrimordialGear` (affinity component, pearls returned: 3 per armor piece, 2 per weapon) with the armor. Plain use blocks; the affinity cycles through the TG ability menu with the weapon in hand. 1.7 sword blocking halved all damage, so the three weapons carry a `blocks_attacks` component (`platform/WgBlocking`, 180 degrees, factor 0.5, no item damage); Terra stacks resistance while blocking. Affinity effects are applied in `AttackEntityEvent` on the server; the Aer sweep hits living entities within 2 blocks of the target except the target itself (the vanilla hit keeps its cooldown and crit). The greataxe wears the target's boots, leggings and chestplate by 5 like the intended WG code (WG damaged the axe instead and could delete the target's armor when the axe broke). Hammer and greataxe break a 3x3 plane from `BreakBlockEvent` through the `primordial_hammer_mineable`/`primordial_greataxe_mineable` block tags instead of WG materials, each extra block goes through the break event and drops with the tool's enchantments, without tool damage or experience, like WG `harvestBlock`. Claymore heads keep WG's quirk of giving a killed player the killer's head. Ordo awards four times `getExperienceReward` extra.
- Status effects (`effects/`): dissolve deals the base `thaumcraft:dissolve` damage every `40 >> amplifier` ticks, so the base liquid death drop of crystallized essence applies; cinder coat multiplies fire damage by 2 + amplifier.
- Alchemy (`alchemy/`): transmogrification and cinnabar purification are plain crucible recipes (cinnabar ore by the `c:ores/cinnabar` tag). The rose vine stores its growth in `age` and its supports (floor and the four walls, read like WG `isSideSolid`, including the WG west/east checks of the far face) in booleans; the WG `BlockRenderRoseVine` boxes live in `tools/rose_vine.json` (extracted once from the WG renderer) and `gen_alchemy.py` builds one floor and four wall models per age as a multipart blockstate. The item is the flat grey `rosevine.png` with the vanilla vine colour as a constant tint (WG drew a 3D inventory model). Its outline is a full block, it has no collision, hurts living entities for 1 inside it, drops only to shears, climbs one block up at age 5 with a 1 in 4 chance per random tick when a wall continues above; a wand spreads it in creative.
- Essentia pump (`devices/EssentiaPumpBlock`): faces the player's look direction and outputs only on that side; it reads the suction of the neighbour there and takes one essentia from a visible base essentia mirror in the 17x17x7 box behind it (WG's line of sight check keeps its bug of using the pump's height for the mirror end). The WG TESR is drawn by `client/devices/EssentiaPumpRenderer` quad by quad (`PumpGeometry`, alembic funnel and alchemy block nozzle) with the four base bellows (`AlchemyRendering.bellows`, orientation down; inflation cycles between 0.35 and 0.65 with the TC4 bellows rates (0.075 down, 0.025 up per tick) on the client clock; WG drew a never ticking fresh `TileBellows` at full inflation, which covered the nozzle and did not move); the item uses the same renderer as a special model. The block model is empty and the hitbox is a full block (WG trimmed it by facing). Research is hidden without mirrors.
- Infernal blast furnace (`furnace/`): one block with `position` (WG `TileEntityBlastfurnace.position`, `yy*9 + (zz+1)*3 + (xx+1)` around the bottom centre master 4) and `heat` (off, on, special) in the blockstate; the WG `getTexture` table becomes 81 models in `gen_furnace.py`, and the master writes `heat` to all 27 blocks when it starts or stops. The structure is the WG one without Railcraft (nether bricks, obsidian, soul sand, nether brick stairs facing the middle, lava on top) and forms through a base wand trigger with the WG cost and 3 sticky warp; the facing (output side) is towards the player. Breaking any part restores the others (`affectNeighborsAfterRemoval`, the loot table drops the original block of that position); WG restored the master even when it was the broken block, which duplicated the obsidian. Recipes live in `BlastFurnaceRecipe` with item ids or `#tags` resolved at use (steel, tungsten and titanium only exist with other mods). WG drew essentia only through the port facing the output side and its tick check was mis-parenthesised; every side port here draws Ignis every 5 ticks from the transport in front of it. The WG output effect was unreachable and is not drawn.
- Terraformer (`terraform/`): the WG metal device metas became the `terraformer` block and one block per focus (`TerraformFocus`: aspect, biome, displayed block). The terraformer reads the focus above, pulls its aspect from the essentia transport below every 5 ticks, and every 20 ticks spends 4 essentia and 4 Terra vis to set the biome column of a random spot within 16 blocks through the base `BiomeEdit` (up to 40 tries to find a spot of another biome). Hell is nether wastes, cold taiga snowy taiga, taint the base `thaumcraft:tainted_land`. The WG vent particles were spawned on the server and never reached clients; they come from a block event here. The WG OBJ (`obj/terraformer.obj`, parts `main_01`, `crystals_02`, `focus_03`, `focus_crystal_04`) is drawn by block entity renderers through the base `ObjModel` with the crystals tinted by the aspect, the focus spins its displayed block above it, and the items use the `witchinggadgets:terraform` special model. All foci use the WG small focus outline (WG left the taint and mushroom foci full blocks).
- Primordial gauntlet (`primordial/PrimordialGauntletItem`): five gem sockets (`gauntlet_gems`), the selected socket and the captured node (`gauntlet_node`, WG primal reduction with the modifier factors and the square root). Using it fires the selected gem through `GemEffects` and adds its charge as damage without ever breaking it; every 10 ticks the node repairs each socketed gem by the node's amount of its aspect (also inside an open gauntlet menu). WG reused the TC4 focus key for its gem radial; here the gauntlet key (V) holds the same radial (`client/primordial/GauntletKeys`: `gauntletradial0/1`, WG gem positions and angle sectors, speed `gemRadialSpeed` in the client config, mouse released when open, left click selects), sneak + key or sneak + use opens the sockets. The item is the WG OBJ drawn by a special item renderer (guards, fingers with the pulsing overlay, runes, and the gems of sockets 2 to 4 on the existing `Gem01`..`Gem03` parts; WG asked for `Gem0N_oval0N` parts the OBJ does not have, so it never drew gems); the finger curl while using is not drawn. The GUI and fixed display keep the rotation of the WG inventory transform composed with the Forge 1.7 inventory block helper (210/45 degrees, flip), but the translation and scale are refitted so the OBJ box is centred in the 16 px slot (the literal 1.7 offsets put it outside the slot, where the GUI item pass clips it). The OBJ is a player arm (`Arm_00` is the 4x12 arm box, shoulder at y 0), and WG drew it over the arm: the third person display is the exact inverse of the vanilla `ItemInHandLayer` hand offset, so the glove sits on the arm part (arm local `T(-1/16, -2/16, 0) * Ry(90)`), the same values for both hands because the left-hand fix mirrors them. First person `client/primordial/GauntletHandRenderer` cancels `RenderHandEvent` and repeats the 1.7 first person item transform (`ItemRenderer.renderItemInFirstPerson`, the Forge -0.5 helper) and the WG `EQUIPPED_FIRST_PERSON` one literally with the 1.7 swing and equip motion (the same formulas as vanilla `ItemInHandRenderer`, from `RenderHandEvent` swing and equip progress), mirrored for the left hand, and draws the WG selected gem glow and the stored node in hand from `nodes.png`; the two WG scales (2, 2, -2) and (-1, 1, 1) sit on both sides of the translate and must not be merged. The arm is the OBJ `Arm_00` part with the player skin like WG (not the vanilla arm model, which does not fit the glove), drawn before the (-1, 1, 1) scale; its UVs are for 64x32 skins, so v is halved for 64x64 skins and the right arm region is used for both hands like 1.7. The gauntlet menu draws the stored node like WG (aspect layers from the base `textures/misc/nodes.png`, core row by node type) and the WG node tooltip with type colours and the shift hint.
- Research-less WG items (`food/`): thaumium shears (thaumium durability 400, vanilla recipe, shear tag, `platform/WgTools.shears`), sweetwart and nethercake with their WG vanilla recipes, and brain jerky, which only TConstruct's drying rack made in WG: it is registered with its food values and the 1 to 3 random primal pool points, hidden from the creative tab and has no recipe.

## Thaumonomicon search

- `client/research/ThaumonomiconSearch` is the WG `ThaumonomiconIndexSearcher` on screen events of the base `ResearchBrowserScreen` (the base is not edited): the field sits in the top frame of the pane (pane size read by reflection, the browser stretches with the window) and is drawn again after the screen, because the browser paints over its widgets; clicks and typed characters are routed to the field by hand, since the browser handles the mouse itself. Results (completed research by name or by recipe outputs, WG `Item:` lines) go right of the pane or inside it when there is no room. The query survives opening a research page; `limitBookSearch` is the WG option in the client config.

## Recipe viewers

The addon adds only the WG NEI categories: spinning wheel and infernal blast furnace. `recipeview/WgRecipeCatalog` is the only data source and holds the WG NEI layout (background `gui/nei/*.png` from (5, 11), NEI slot positions); `client/jei` and `compat/rei` (displays, serializers by recipe key) + `client/rei` only draw it. ## Travellers' Gear

- `travellersgear/TravellersGearFeature`: TG simple gear (`traveller_cloak` dyed through `minecraft:dyed_color`, 16 wool recipes with the TG colours; `belt`, `gold_ring`, `silver_ring` (recipe only with `c:nuggets/silver`) as base baubles; `pauldron`, `vambrace`; `title_scroll` with the 11 TG titles in the WG `title` component). TG assets come from `reference/tg-src` through `convert_assets.py` into `textures/*/travellersgear/`, TG lang keys (`TG.*`) pass through, simple gear names map to the addon ids. Chest loot uses `gen_resources.inject_loot` with the 1.7 table weights (TG weight 8 per title split over 11 entries).
- Titles of other players are drawn one line under the name tag (`client/travellersgear/TitleRenderer`, `RenderNameTagEvent.DoRender`), not for the own player or while sneaking.
- Simple gear models: the TG cloak reuses `CloakGeometry` with `models/travellersgear/cloak.png`; pauldrons (grow 0.5, 1.125 over a chestplate), vambraces and the belt are `ModelSimpleGear` boxes in `client/baubles/BaubleLayer` on `tgtextures.png`.
- Ability menu: `gear/GearAbility.canActivate(player, stack, inHand)` and `gear/AbilitySlots` (TG slot codes: hotbar, armor 9..12 boots first, baubles 13+, gear 100+; the held item sits in the middle like TG); `ActivateAbilityPayload` re-checks on the server. `AbilitySlots.register` adds abilities to foreign items: the base focus pouch in a bauble slot opens like the WG coremod patch. `client/travellersgear/AbilityRadial` is the TG wheel (key R, radial speed in the client config, mouse released when fully open, left click selects, the key again closes) drawn with `client/platform/WgGuiQuads` and the base `GuiLines`.
- Inventory: `platform/gear/GearMenu` has the TG slot order (result, 2x2 crafting, armor, TG gear, 4 baubles, inventory, hotbar). Slot positions come from `GearMenu.layout`, which the client sets to `client/travellersgear/TgLayout` (TG default and the presets Book, Digital, Epic Quest extracted by `convert_assets.py` from `CustomizeableGuiHandler.java` into `travellersgear/layouts.json`; the user layout is saved to `config/witchinggadgets-travellersgear-inventory.json`). Hidden slots travel to the server as a mask in `OpenGearPayload` and become inactive slots. `/travellersgear gui` opens the layout editor (drag, Ctrl/Shift lock an axis, right-drag selects, hide box), `/travellersgear toolDisplay` the tool display editor. Ctrl + right click in the TG inventory sends `ShowItemPayload` (the server reads the item from the open menu, one per second).
- Tool display: up to 6 `travellersgear/ToolDisplay` entries per player in the `tool_display` attachment (synced to all, copied on death), set through `SetToolDisplayPayload` (clamped), drawn by `client/travellersgear/ToolDisplayLayer` with the TG transform order.

## Generated files (do not edit by hand)

| File | Generator |
|---|---|
| `src/main/resources/assets/witchinggadgets` (textures, `obj`, lang) | `tools/convert_assets.py` (+ `tools/assets_extra/`, `tools/lang/`) |
| `src/generated/resources` (rewritten completely) | `tools/gen_resources.py` |
| `reference/wg-src` | `tools/fetch_wg.py` |
| `reference/tg-src` | `tools/fetch_tg.py` |
| `tools/wg_research.json` | `tools/extract_wg_research.py` |

- After a lang change: `convert_assets.py`, then `gen_resources.py`. Manual translations only in `tools/lang/<lang>.json` and `tools/lang/<feature>/<lang>.json`. WG has no Russian, `ru_ru` exists only from `tools/lang/` and is translated by us; base terms are reused (Arcane is «магический», Primordial and Primal «сингулярный», Taint «заражённый», Void «пустотный», Thaumium «таум-»).
- The WG `.lang` files are UTF-8 with a few cp1252 lines (comments, umlauts in `de_DE.lang`), `convert_assets.py` and `inventory.py` decode UTF-8 with a `cp1252_fallback` error handler (invalid bytes are read as cp1252, also inside a mixed line).
- Some WG `.mcmeta` files are lenient JSON (`{index:0, time:120}`), `convert_assets.py` quotes the keys.
- Lang keys: blocks `block.witchinggadgets.<id>`, items `item.witchinggadgets.<id>`, a `variant` row in `id_map.json` gives `item.witchinggadgets.<id>.<variant>` (`infused_gem.inert`). Research `witchinggadgets_research_name.KEY` becomes `tc.research_name.KEY`, `_text.KEY` `tc.research_text.KEY`, `_page.KEY.N` `tc.research_page.KEY.N` with the WG suffix kept (`1`, `2`, `r1`), pages are referenced by the full key. Category `tc.research_category.WITCHGADG`. Enchantments `enchantment.wg.camelCase` become `enchantment.witchinggadgets.snake_case`. `wg.*` keys stay as they are, anything else gets the `witchinggadgets.` prefix.
- Textures are copied with `blocks` renamed to `block`, `items` to `item`, names lowercased; `models` and `gui` keep their folder names. `.obj` models go to `assets/witchinggadgets/obj/<snake_case>.obj`.
- The resource format profile lives in `tools/mcformat.py`.
- Block models see only the block atlas: a `textures/models` texture used by a block model is copied to `textures/block` with `ctx.block_texture`, and `gen_resources.py` fails on any `witchinggadgets` texture outside `block/` and `item/`.

## id_map.json

- Edited by hand. A row: `old` (WG registration name), `meta`, `lang` (en_US.lang key or null), `id`, `state` (blocks only), `skip` (reason or null), optional `no_item` (block without an item) and `variant` (an extra lang key of an existing id).
- Ids are the snake_case registration sub-name when it is meaningful, otherwise the lang name: `timeStone` is `ageing_stone`, `cobbleGen` `stone_extruder`, `calculator` `arcane_abacus`, `CrystalFlask` `crystal_capsule`, `blastFurnace` `infernal_blast_furnace`. The three `obsidianDecoration` metas are `obsidian_rune_0..2`.
- Skipped: the hidden `snowGen`, raven cloak and kama (need Twilight Forest), native clusters of other mods' ores (`WG_Cluster`), and stale lang keys of content WG 1.1.10 does not register (loom, armor stand, elite armor, scribing tools, primordial and life protection rings, old material clusters). Every tile/item `.name` key of en_US.lang must be covered by a row, `inventory.py --check` verifies it.

python3 tools/fetch_wg.py
python3 tools/convert_assets.py
python3 tools/gen_resources.py && git status --short src/generated
python3 tools/extract_wg_research.py && git status --short tools/wg_research.json

python3 tools/check_seams.py
./gradlew build

- Regeneration must not change files.

- Visual checks in `runClient` and two-client play are done by the user.
